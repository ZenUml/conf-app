# AI Repair Continuous Improvement

This skill is a bounded improvement batch: find real failures → preserve original cases → assign work → fix → validate each layer → save the final L4 preview → optionally run regression with [ai-repair-regression](../ai-repair-regression/SKILL.md). **When the request is only for simple or full regression on saved historical error DSL, use that standalone skill directly**; do not enter this skill's production data retrieval flow. When invoked again, resume from the saved corpus and unfinished cases. Do not present a single run as a scheduled automated task.

At the start, locate both the conf-app and diagramly.ai checkouts and verify their remotes and project instructions. Relative paths below are based on conf-app; Diagramly paths are identified explicitly. If either checkout is missing, report the blocker instead of guessing its path.

## First report counts for the requested period, then ask three questions

First obtain the time range specified by the user. If none was provided, ask only for the start and end times and timezone; do not guess what “recent” means. Run the **read-only aggregate query** for production Jobs described in [Production intake](references/production-intake.md#count-first). Report the number of failed jobs, the number of distinct failed DSL inputs, and the number of identifiable COMPLETED no-ops in that range. Do not export DSL bodies, create case tasks, or call AI at this step. Tell the user the time range, filtering criteria, and query time. If production is inaccessible, say the counts are unknown; do not substitute Mixpanel event counts for DSL counts.

After obtaining the counts, ask the user all three questions below in one message and wait for their answers. Do not fill in defaults:

1. Of the newly failed DSLs just counted, how many may this run process at most, and how many AI repair calls (or tokens/cost) may it use at most? If the private index is readable, also report the number of existing pending cases. Track the two limits independently. If either limit is reached, pause and leave remaining cases in the candidate queue; do not exceed a limit through repeated retries. With a call-count budget, reserve each call before making it. With a token/cost budget, estimate and reserve the maximum cost of the next call; if that cannot be estimated, verify it first or stop.
2. Does the user authorize sending each selected case's complete original DSL, actual parser error, and constructed AI Repair Prompt to the AI repair service during this run? Identify the actual service, model, and routing path (for example, local Diagramly → OpenRouter → selected model). Limit consent to the cases and model selected for this run. If the user declines, data retrieval, saving, and offline analysis may continue, but all L2/L3/L4 model calls and regression calls remain BLOCKED (no_model_authorization). Authorization from an earlier batch does not carry over.
3. After all fixes are complete, should the latest AI Repair Prompt be regression-tested? If yes, ask the user to choose **simple regression (L2 only)** or **full regression (L2 → L3 → L4)**, and confirm whether to cover all saved cases or a user-specified maximum number of historical cases. Explain that `ai-repair-regression` runs the regression, uses the model-call budget from item 1, and that full regression also requires authorization to use L4 test-site data. Do not choose a mode for the user. If no, record SKIPPED (user_declined). If not all cases are fixed, record that the trigger condition was not met; do not call partial testing final regression.

Create this run's record at private runs/<run-id>/run.json. Record the time range, aggregate counts and criteria, all three answers, selected regression mode, case IDs, actual model/destination, task IDs and statuses, regression scope, and remaining budget. Do not overwrite a root-level run.json or a previous batch. Parallel tasks must reserve calls with the main session, which tracks deductions in one shared budget ledger; they must not spend a separate global allowance. If the authorization scope for item 2 is unclear, verify the destination and data scope before calling the model. Model-call authorization does not authorize commits, pushes, deployments, page publishing, or scheduled tasks.

## 1. Find and preserve failures

After all three answers are clear, use [Production intake](references/production-intake.md) to inspect Mixpanel lifecycle signals and Diagramly production Jobs. Mixpanel contains neither DSL nor jobId; use Job.input.diagramCode as the source text. Include FAILED jobs, and inspect COMPLETED jobs that returned the original input or whose candidate still cannot be parsed/rendered. Distinguish frontend failures that have no backend Job. Production access must remain read-only; use the already-counted time window and bounded pagination, stopping at the user's case limit.

Save each selected original DSL and any available actual errorMessage byte-for-byte under conf-app's private/local-data/ai-repair-regression/. If an error is missing, mark the evidence gap; do not invent one. Follow the existing corpus.json and separate case-directory structure. Append the source job, time, language, model, status, input SHA-256, and selection rationale. Preserve source records for repeated identical inputs with different errors or attempts; never overwrite originals or historical results. Save candidate fixes separately from original inputs. This directory is a persistent local regression corpus; it must not enter the public repository or be committed to the private submodule. If the directory is unavailable, stop at a safe local private path and report that migration is needed; do not save the data in the public repository.

## 2. Coordinate task sessions

Follow [Task assignment and acceptance](references/task-coordination.md) to write a clear task for each independent case or group of cases sharing a root cause. Specify the fixed original DSL/error, source record, model and limits, permitted files, acceptance evidence, and private artifact directory. The main session owns the corpus index, shared Prompt changes, final decisions, and L4 browser. Delegate simple retrieval, organization, and deterministic checks to lower-cost subagents; the main session handles deeper diagnosis and integration.

Create and coordinate multiple Codex task sessions only when the user explicitly requests them; otherwise divide work among subagents within the current task. Each session may access only its assigned customer cases. Do not paste DSL into the public repository, PRs, task titles, or ordinary messages; hand off using absolute local private paths. Tasks must not concurrently edit the same Prompt/file, share a browser, or compete for the same local service. Queue conflicting tasks and integrate them one at a time in the main session. Do not create Git branches or worktrees without user confirmation. Preserve existing workspace changes.

## 3. Fixes and layer gates

For each case, use the default L2 → L3 → L4 flow in [ai-repair-case-validation](../ai-repair-case-validation/SKILL.md). A strong-model retry tests L2 only by default; continue further only when explicitly requested. Before running, read the current model configuration in src/utils/aiModelConfig.ts. Generate the actual Prompt from the current Diagramly checkout; do not copy it by hand. Record both repositories' HEAD/dirty state, Prompt hash, parameters, each raw output, parsing/rendering evidence, and cost source. For no-ops, empty output, syntax errors, lost anchors, or job/UI failures, improve the earliest failing layer and retest. If a layer has not passed, mark the next layer SKIPPED. Check and deduct from the shared call budget before each retry. When the budget is exhausted, save state and stop; do not mark PASS. A successful model response or unit test does not replace UI evidence.

L4 is determined only by an actually visible browser result. Putting production customer DSL into a test Confluence macro sends it to another data destination. Before L4, tell the user the specific site and whether a draft will remain, and obtain separate confirmation; authorization for item 2 does not cover it. Without confirmation, record L4 as BLOCKED (no_ui_data_authorization). After confirmation, reuse the current logged-in browser tab under the project browser rules. If it cannot be controlled, use the Codex built-in browser at the standard desktop viewport. Run cases serially. Save error states, diff states, the real preview screenshot from the last successful repair after Apply Code, and network/model evidence under that case's l4/<run-id>/. Also write final-preview.json pointing to the final PASS screenshot and recording the repaired DSL SHA-256, model, Prompt hash, time, and corresponding l4/results.jsonl record. Keep earlier failure screenshots; do not overwrite history. Without a real preview, do not write final-preview or mark L4 PASS. By default, leave only a macro draft; do not publish a Confluence page.

## 4. Final regression and delivery

Only when every case selected for this batch has reached L4 PASS, and the answer to item 3 is yes with a regression mode selected, run [ai-repair-regression](../ai-repair-regression/SKILL.md) on the user-approved historical scope using the final code/Prompt. Hand that skill the selected cases, current code/Prompt version, this run's model and data-authorization scope, remaining shared budget, and before/after evidence. Regression cannot receive a separate full budget. If historical cases fall outside the existing data authorization, obtain the relevant authorization first. Preserve evidence and return to the fix loop if regression finds a regression. Pause if the budget is insufficient; do not report “entire corpus passed.”

Deliver the private corpus index, each case's status/task session, repair changes, L2/L3/L4 repair-validation evidence, and final preview paths. If final regression ran, also include the independent skill's regression evidence and covered/uncovered lists. A historical successful L4 preview is not L4 regression evidence for the new Prompt. Report only observed results; do not infer an overall success rate from a small sample. Unless separately and explicitly requested, do not commit, push, deploy, send external messages, or schedule recurring runs.
