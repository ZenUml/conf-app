# AI Repair 持续改进

本 skill 是一次有上限的改进批次：发现真实失败 → 固化原始案例 → 分配任务 → 修复 → 逐层验证 → 保存最终 L4 预览 → 可选地用最新 Prompt 回归。再次调用时从已保存语料和未完成案例续做；不把一次运行伪装成定时自动任务。

开始时定位 conf-app 与 diagramly.ai 两个 checkout，核对远端地址和项目指令；下文相对路径均以 conf-app 为基准，Diagramly 路径会明确说明。若缺少其中一个 checkout，报告阻塞而不猜路径。

## 先按指定时间统计，再问三件事

先取得用户指定的时间范围；用户尚未给出时，只问起止时间和时区，不猜测“最近”代表多久。按 [线上取数与入库](references/production-intake.md#先统计数量) 对生产 Job 做**只读聚合查询**，输出该范围内失败 job 次数、去重后的失败 DSL 数，以及可识别的 COMPLETED no-op 数。此步不导出 DSL 正文、不创建案例任务、不调用 AI。把时间范围、筛选口径和查询时刻一同告诉用户；无法访问生产时说明数量未知，不用 Mixpanel 事件数冒充 DSL 数。

拿到数量后，向用户一次问清下面三件事并等待回答，不能代填默认答案：

1. 在刚统计出的数量中，本轮最多处理多少份新的失败 DSL，且最多允许多少次 AI 修复调用（或多少 token/费用）？纯历史回归可答 0 份新案例；模型预算要大于 0。若可读取私有索引，同时说明已有待处理案例数。两个上限独立记录，超过任一上限就暂停并留在候选队列，不能靠反复重试突破额度。按调用次数计时每次调用前预约；按 token/费用计时先估算并预留该次最大消耗，无法预估就先核实或停下。
2. 是否授权本轮将这些案例的完整原始 DSL、真实解析错误及构造出的 AI Repair Prompt 发送给 AI 修复服务？说明实际服务、模型及转发路径（例如本地 Diagramly → OpenRouter → 所选模型），把“同意”限定为本轮选中的案例和模型；拒绝时仍可只读取数、保存和离线分析，但所有 L2/L3/L4 模型调用与回归调用保持 BLOCKED (no_model_authorization)。旧批次的授权不能沿用。
3. 全部修复完成后，是否用当时最新的 AI Repair Prompt 做回归测试？若“是”，请用户同时选择**简易回归（仅 L2）**或**完全回归（L2 → L3 → L4）**，并确认是全部已保存案例，还是用户指定的历史案例数量上限；说明两种模式都会占用第 1 项的模型调用预算，完全回归还需要 L4 的测试站点数据授权。不得代用户选择模式。若“否”则记录 SKIPPED (user_declined)。未全部修复时记录未达触发条件，不把部分测试称为最终回归。

在私有 runs/<run-id>/run.json 新建本轮记录，保存时间范围、聚合数量及口径、三个回答、用户选择的回归模式、所选案例 ID、实际模型/目的地、任务 ID 与状态、回归范围和预算余额；不要覆盖既有根目录 run.json 或历史批次。并行任务必须向主会话预约调用配额，由主会话在单一预算台账中扣减，不能各自独立使用全局额度。若第 2 项授权范围不清楚，先核实目的地和数据范围再调用模型。授权模型调用不代表授权提交、推送、部署、发布页面或创建定时任务。

## 1. 发现并固化失败

在三个回答明确后，按 [线上取数与入库](references/production-intake.md) 查 Mixpanel 生命周期信号和 Diagramly 生产 Job。Mixpanel 不含 DSL 或 jobId；原文以 Job.input.diagramCode 为准。纳入 FAILED，也检查 COMPLETED 却原文返回、候选仍无法解析/渲染的假成功。区分前端失败但没有后端 Job 的缺口。生产只读、沿用已统计的时间窗口、分批分页，到用户给出的数量上限为止。

将每份被选中的原始 DSL 和可取得的真实 errorMessage 按原字节保存到 conf-app 的 private/local-data/ai-repair-regression/；错误缺失时标记证据缺口，不自行编造。沿用现有 corpus.json 与独立 case 目录；追加来源 job、时间、语言、模型、状态、输入 SHA-256、选择理由。相同输入要保留不同错误与尝试的来源记录，不覆盖原文或历史结果。候选修复与原始输入分文件保存。该目录是本机持久回归语料，不进入 public repo，也不提交到 private 子模块。若目录不可用，停在安全的本机私有路径并报告迁移需求；不要改存公开仓库。

## 2. 协调多个任务会话

按 [任务分配与验收](references/task-coordination.md) 为每个独立案例或同根因案例组写明确任务：固定原始 DSL/错误、源记录、模型和上限、允许的文件、验收证据、私有产物目录。主会话保管语料索引、共享 Prompt 的修改权、最终判断和 L4 浏览器。简单取数、整理、确定性验证可交给低成本子代理；需要深入诊断或整合的工作由主会话处理。

用户明确要求新建多个 Codex 任务会话时，创建并协调这些会话；否则在当前任务内用子代理分工。会话只能读取自己分配的客户案例；不要把 DSL 贴在公开仓库、PR、任务标题或普通消息中，用本机私有绝对路径交接。任务之间不能同时改同一 Prompt/文件、使用同一浏览器或抢占同一本地服务；冲突任务排队，主会话逐个整合。未经用户确认，不自动创建 Git 分支或 worktree。保留现有工作区改动。

## 3. 修复与分层门槛

每例调用现有 [ai-repair-case-validation](../ai-repair-case-validation/SKILL.md) 的默认模型 L2 → L3 → L4 流程；强模型重试默认只测 L2，明确指定后才继续。运行前读取 src/utils/aiModelConfig.ts 的当前模型配置；从当前 Diagramly checkout 生成真实 Prompt，不手抄。记录两个仓库的 HEAD/脏状态、Prompt hash、参数、每次原始输出、解析/渲染证据和成本来源。修复 no-op、空输出、语法错误、锚点丢失、job/UI 失败时，从最早失败层改进并重测；上一层没有 PASS，下一层 SKIPPED。每次重试前检查并扣减共享调用预算，额度耗尽就保存状态并停止，不能标 PASS。不要以模型返回成功或单元测试代替 UI 证据。

L4 只由浏览器中实际可见的结果判定。把生产客户 DSL 放入测试 Confluence 宏是另一个数据目的地，执行 L4 前单独告知具体站点和是否会留下草稿并取得用户确认；第 2 项的 AI 服务授权不覆盖它。未经确认，L4 记 BLOCKED (no_ui_data_authorization)。获确认后按项目浏览器规则复用当前登录标签，无法接管时使用 Codex 内置浏览器的标准桌面视口；串行执行各案例。保存错误态、diff 态、Apply Code 后最后一次修复成功的真实预览截图及网络/模型证据到该案例的 l4/<run-id>/。另写 final-preview.json 指向最终 PASS 截图、修复后 DSL 的 SHA-256、模型、Prompt hash、时间和对应 l4/results.jsonl 记录；保留之前失败截图，不覆盖历史。没有真实预览则不得写 final-preview 或 L4 PASS。默认只保留宏草稿，不发布 Confluence 页面。

## 4. 最终回归与交付

仅当本轮选中的案例全部完成 L4 PASS，且第 3 项回答为“是”并已选定回归模式，才用最终代码/Prompt 对用户确认的回归范围重跑。默认建议包含全部已保存历史案例以防旧问题复发；若用户给出数量上限，按最早失败、不同 DSL 类型和最近退化覆盖取样并列出未覆盖案例。重新生成每例 Prompt hash，以同一默认模型运行所选模式，不把参考修复传给模型：**简易回归仅执行 L2**，将该轮 L3/L4 记为 `SKIPPED (simple_regression)`；**完全回归依次执行 L2 → L3 → L4**，遵守逐层 PASS 门槛和 L4 测试站点数据授权。逐例对比修复前、最后一次修复和最终回归，发现退化就回到修复循环，并保留失败证据。模型调用预算不足时暂停并等待补充额度，不能报告“全语料通过”。

交付私有语料索引、每例状态/任务会话、修复改动、L2/L3/L4 修复验证证据、最终预览路径、回归模式、该模式的回归证据、覆盖与未覆盖清单。简易回归通过只能说明最新 Prompt 的 L2 通过；此前保存的 L4 成功预览仍是修复验证证据，不能当作最新 Prompt 的 L4 回归结果。只报告实际观察，不从少量样本推断总体成功率。未经另行明确要求，不提交、推送、部署、对外发送消息或设置周期运行。
