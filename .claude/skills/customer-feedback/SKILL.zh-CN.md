技能名称：customer-feedback

用途：在 Marketplace 取消原因、Mixpanel 满意度提交、D1 产品内功能/问题报告和支持对话之间，查找并核对客户明确表达的反馈。适用于近期反馈、未满足的需求、功能请求、试用或流失调查以及产品研究。把用户观点和行为证据分开，并保留各来源的覆盖情况。

# 客户反馈

先读[共享证据和来源规则](../customer-data/evidence.md)。按站点/产品、时间窗口和问题限定范围。"最近"可以简化为完整的 7 天；做研究时使用用户要求的 30/90 天周期或事件窗口。这是只读调查，不代表获准联系客户。

## 运行约定

一次运行内跑完全部四个来源（Marketplace、Mixpanel、D1、Gmail/support），中途不询问。默认范围：所有产品和站点，最近 30 天。只有用户排除的来源才能标为 `not_queried`；其他来源要报告 `failed`/`unavailable` 并附上错误。Gmail 要读到第一页之后，或者写明已读线程数 / 估计总数。不要以提问结束。

## 来源

| 来源 | 要取回的内容 | 边界 |
|---|---|---|
| Marketplace | 取消/退订原因、客户自由文本、产品/订阅和反馈日期 | 只有状态变化没有客户解释；取消不一定等于卸载 |
| Mixpanel | 真实的满意度提交、选项/分数/文本，以及当前事件目录支持的身份字段 | 打开/点击/错误描述的是行为，不是表达的意见；提交流程本身不算另一条反馈 |
| D1 产品内反馈 | 功能请求、问题、描述、入口位置、产品/站点/用户上下文、报告引用和可选附件 | 不限于满意度；查询前先核实表、部署和覆盖范围 |
| Gmail/支持工单 | 相关邮件、真实发件人、引用的需求、回复、解决情况和承诺 | 之前 agent 的摘要只是搜索线索；声称当前结果前要读原始线程 |

## D1 能力检查

先检查当前 schema/migrations 和已部署的查询权限。只存在于另一个 checkout 中的 `FeedbackReport` 工作，不能证明生产环境支持。使用已配置的只读 D1 查询路径，在 select 之前先查看表的列；不要编造列名，也不要把表不存在或查询失败当作没有反馈。截图的保留期和报告的保留期分开记录；除非调查需要，不要下载或暴露附件。现有的 CSAT 和功能反馈是两个不同的入口。

## 收集与核对

1. 根据已核实的标识确定站点和产品。缺少证据时，联系人角色保持不确定。
2. 在所选窗口内取回原始反馈记录，以及解读它们所需的周边线程或行为窗口。访问时使用现有的 `marketplace`、`mixpanel`、`conf-app` 和对话工具，不要新建凭据或重复导出。
3. 在明确标注的字段中保留用户原话；另外分类为功能请求、bug、未满足需求、可用性、满意度、采购或其他。解读放在另一个字段。
4. 只有存在已核实的共享报告/消息引用时才关联记录。同一用户/站点/时间最多算疑似关联。一条 D1 报告加一条没有共享引用的 Mixpanel 提交成功事件，仍然是一条明确报告加一个可能相关的流程事件；不要把后者算作第二条意见，也不要悄悄合并。
5. 行为可以提示该问什么，但不能说明客户为什么取消。例如，PNG 下载成功和邮件导出失败是不同动作；两者都不能证明未满足需求回答的原因。

## 返回

返回共享信号字段，再加上反馈类别、原文引用、解决/回复证据，以及和其他记录的关系（`verified`、`suspected`、`unrelated`）。把明确反馈的总数和行为/流程事件分开。包含各来源的新鲜度，以及 successful-empty / failed / unavailable / not-queried 覆盖情况。不要把缺失的来源总结为"没有反馈"。

当用户还需要排优先级、沟通或更新跟踪表时，使用 `customer-followup`；同一份证据应复用，不要重新查询没有变化的来源。
