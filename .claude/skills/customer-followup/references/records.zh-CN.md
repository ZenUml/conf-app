# 可迁移的客户记录约定

存储适配器把这些业务含义映射到当前表头，不能依赖固定列字母或行号。编辑前重新读取表头，按稳定 ID 找行。ID 缺失或重复时应明确报错；不能只凭显示名称相似就选中客户。

## 机会摘要

每个“客户站点＋产品＋商业目标”对应一个机会。相关空间归入同一机会，除非存在独立购买流程，确有理由拆分。可以比较 Full 和 Lite 的使用，但许可及事件必须保留各自版本身份。

- 稳定机会 ID；公司／域名及已核实站点标识；产品；目标／类型。
- 机会阶段：待确认需求、已联系、等待客户、确认购买条件、采购中、已成交、明确拒绝、暂缓。对于购买／续费目标，匹配到有效非零订单且商业许可已生效，即可确认已成交，不受 Open 结算状态影响。退款／取消／仅免费记录，以及没有订单证据的商业许可，都不满足此条件。商业成交不会结束尚未解决的技术工作。
- 许可摘要、付款状态和证据日期分别记录。付款状态区分：未检查、未找到匹配交易、交易已记录但结算未确认（保留 Open／未知）、来源明确报告已付款、部分付款、已退款。不得把未知当作未付款，也不得把已有 Open 订单称作“无付款记录”。来源报告已付款不证明供应商银行已到账。
- 当前障碍、下一动作、负责人、下次审阅日期及明确时区。
- 主要联系人、决策人和职责证据；职责未知是有效状态。
- 潜在年化价值、币种，以及估算／标价／报价／合同的依据和日期。它不是已收收入。
- 证据链接和最近一条有意义记录的引用。
- 暂缓原因及可观察的恢复条件，或结果日期及结束原因。

摘要保持简短。完整消息留在 Gmail／工单，许可／交易留在其来源系统，较长分析放入私有 Handbook 文件。归档资料不等于已刷新的事实。

后续全额退款／交易冲销是新结果，不表示历史购买从未发生。保留历史，记录退款和当前许可事实，不把它表述为仍然保有的有效成交。如果当前跟进工具没有能准确表达退款／冲销的阶段，应指出映射缺口，不能编造客户拒绝，也不能自动重启销售跟进。

## 活动记录

每次有意义的真实沟通、信号核验或决定追加一行。包含记录日期、机会 ID、联系人、渠道、事实摘要（引用原话时明确标示）、采取的动作、结果／解释、证据链接、负责人、记录类型、动作状态、执行时间／时区及稳定活动 ID。

动作状态：草稿、已定时、已发送、已收到、已取消、失败、待核验、不适用。旧混合记录可保留“见原记录”，迁移时不能编造精确状态变化。保留既有 ID；导入旧历史时明确标记为历史整理，并保留证据日期。

## 安全写入与核验

1. 检查当前值和最新活动。保留无关编辑、公式、格式、验证规则和来源链接。
2. 追加前，把来源消息／工单／事件标识与已有记录匹配。重试不能重复记录已经发送的事件；确实不同的动作应分别保留。
3. 追加已核实活动，然后一致地更新受影响摘要：商业阶段、过时的审批／障碍／下一动作文字，以及必要的结果日期和证据链接。“只刷新状态”排除的是建议或执行新的外联，不排除纠正过时阶段。结果日期使用有证据的商业事件日期；日期未知时明确标记，不把查询时间冒充事件时间。原始结算状态单独保留。仅准备好但未写入的修改，仍标为草稿／待处理，并说明存放位置。
4. 读回保存后的值、记录 ID 和来源链接。结构性调整还要核实表范围、验证值、公式及截图。部分写入应标记为待对齐；未保存成功，不能宣布更新完成。

暂缓和付款不会覆盖沟通历史。公式只是展示辅助，不赋予发送、计费或恢复联系的权限。审阅日期仅安排人工关注，不会创建自动化。

## 何时 Sheets 不再够用

当多个并行购买流程、大量联系人关联、频繁并发写入，或漏做／重复动作无法靠两张表及来源链接可靠管理时，再评估存储工具。迁移到其他 CRM 时保留这套记录约定，不把具体 CRM 的 API 嵌入业务判断政策。
