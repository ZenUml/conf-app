Make “Create Test Page” truthful before making it bigger

The API-only workflow is valuable, but its current interface hides the app variant and can create a page that renders the wrong diagram—or no usable macro at all.

Recommendation: approve a two-step improvement. First make Lite payloads correct and self-verifying. Then make the target explicit as app × environment × site, starting with Diagramly. Adding more site aliases alone would preserve the underlying ambiguity.

Why this matters

The workflow itself works

History shows successful API-created pages on Lite development and Lite staging. The three-request approach is fast and avoids brittle editor automation.

The target is implicit

All four accepted aliases are wired to the Lite app ID, Lite namespace, and Lite macro suffix. A site can host multiple variants, so a site alias cannot identify the app under test.

Some “successful” inputs are wrong

PlantUML was stored as diagramType: sequence and rendered as ZenUML in an August 19 investigation. OpenAPI uses a content type and body shape that do not match the application’s storage contract.

What we should build

1 · Correct the contract

Use a single macro table for sequence, mermaid, plantuml, openapi, and graph. Require at least one macro. Reject unknown or empty files before the first POST.

2 · Make identity explicit

Expose --app, --environment, and --site. Validate the combination against a declarative registry containing app ID, environment ID, namespace, suffix, supported macro types, and content keys.

3 · Verify the result

Read back the created custom content and page ADF. Assert content type, diagram type, source field, and extension key before returning the URL.

4 · Keep test data recoverable

On a later failed request, clean up the page and created custom content where safe. On success, return page ID and custom-content IDs, not only the URL.

Tradeoffs and boundaries

Variant support is configuration work, not a new rendering architecture. It will make the command slightly more verbose and requires verified Forge environment IDs. That cost buys a fail-fast error instead of a convincing-looking page wired to the wrong app.

AsyncAPI should follow only after its API credential profile and custom-content schema are verified separately. The history includes a 403 caused by a tenant/account identity split, so “same token works everywhere” is not a safe assumption for that variant.

There is no UI demo to embed in this pitch: the proposed change is developer tooling and the current API workflow is intentionally browser-free. The repository deviation log is unrelated onboarding work and is not used as evidence here.

Decision requested: approve the contract fix and verification layer as the first slice, followed by an explicit variant-aware registry with Diagramly as the first additional target. Keep Full and AsyncAPI out of the first slice until their identities and schemas are independently checked.
