Problem and value

Useful architecture context is already present, but not yet reusable.

Sequence diagrams frequently name the services and APIs involved in a flow. Today, that context stays embedded in individual diagrams. Architecture Tokens tests whether a small, high-confidence subset can become structured evidence for future discovery work—without asking authors to maintain a second system.

Who benefits if the evidence is strong?

  • Authors, by preserving diagram-first documentation rather than adding data-entry work.
  • Architecture and platform teams, by gaining a more dependable starting point for future discovery.
  • Product teams, by learning whether an eventual architecture experience can be grounded in explicit evidence rather than inference.

What was built

A calibration capability, not an architecture catalogue.

  • Strict eligibility for exactly ten distinct, current Mermaid sequence diagrams.
  • A GPT-5.3 Codex/Spark extraction step constrained to explicit service-level participants.
  • Post-processing that requires literal supporting evidence and prefers abstention over guesswork.
  • Rebuildable, version-aware derived records for calibration review and reruns.

Verified before activation

The full unit suite (259 test files, 3,050 tests), a production-style backend bundle, and the Lite build passed. No deployment, migration, customer model call, production write, or feature enablement was performed.

Scope and safety

Narrow by design.

In MVP-0

  • One approved pilot tenant, identified only in protected runtime configuration.
  • Ten selected current Mermaid sequence diagrams for calibration.
  • Explicit Service, API, and external-service candidate occurrences.
  • Internal review of derived output before any further processing.

Explicitly not in MVP-0

  • Customer UI, editing flow, Viewer, or Catalogue.
  • Final identity resolution, deduplication, or cross-diagram merging.
  • Cross-tenant association or non-sequence diagram ingestion.
  • Any broad batch run before the controlled calibration passes.

Tradeoffs and rejected paths

We chose trustworthiness and reversibility over apparent completeness.

Candidate occurrences, not final identities

We rejected automatic merging or a catalogue because labels alone are insufficient proof that two things are the same architecture entity.

Ten-source calibration, not a broad run

We rejected starting with the wider inventory. Manual comparison gives us a quality signal before more content is processed.

Backend-only, not a premature demo

We rejected a customer-facing surface until the extraction is shown to be accurate, privacy-safe, and useful in reviewed examples.

Controlled activation

The next step is an operator-reviewed calibration, not a launch.

Deploy safely

Deploy the reviewed backend change while leaving the capability disabled.

Configure the boundary

Set protected runtime values for the approved tenant, trusted app, and server-side model access.

Enable deliberately

Turn on execution only when authorized; turn on derived writes separately when needed.

Run exactly ten

Use the tenant-bound trusted executor to submit the approved current sources.

Review and decide

Compare every output to its evidence and record a documented go/no-go result.
