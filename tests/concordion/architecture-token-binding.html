Architecture Token bindings: Flowchart node safety

A binding is to a logical node, never to a source offset and never merely to a Mermaid native ID. A locator only says where the node appeared in one source revision; it is not the node's identity. This specification executes the production canonical Flowchart parser and fail-closed reconciler without Confluence, D1, or a ZenUML backend.

In this first release, strong evidence means a unique source-diff relocation plus an exact node fingerprint. A harmless relocation can retain a binding. A node-label rename is not yet an automatic case; it remains for human confirmation until stronger matching is implemented.

How to read an outcome

Reader-facing resultWhat happens to the existing binding
Auto retainedOnly unique strong evidence proves the same logical node continues.
Needs human confirmationA plausible candidate exists, but the system does not transfer the binding itself.
AmbiguousA split, merge, or one-to-one conflict has more than one safe interpretation.
OrphanedNo safe replacement exists; the old binding is retained as unresolved evidence.
UnsupportedThe source is outside the owned Flowchart subset, so no identity is guessed.

Release boundary

These are Mermaid Flowchart node examples only. Subgraphs and edges are context, not binding targets. No part of this contract writes Confluence content, calls a backend, or creates a global token index.
